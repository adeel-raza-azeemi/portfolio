03. Reverse Engineering the Legacy ERP

"Before data could be consolidated, it first had to be understood."

Unlike greenfield software projects, legacy enterprise systems rarely provide developers with a complete understanding of their internal data model. Documentation may be outdated, source code unavailable, and years of incremental modifications often obscure the original system architecture. Consequently, understanding an existing system frequently becomes the first engineering challenge rather than software implementation itself.

The Employee Search MIS was developed under exactly these conditions.

Although the organization had administrative access to the ERP database, no documentation described how employee information was organized internally. The application source code was unavailable, no entity relationship diagrams existed, and no data dictionary explained how the Human Resource module interacted with the database.

Rather than beginning with software development, the project therefore began with a process of systematic reverse engineering.

3.1 Initial Exploration

Administrative access to the Oracle database made it possible to inspect the database schema directly.

The first inspection immediately demonstrated the scale of the enterprise application.

Database Object Count
Tables 685
Views 187
Non-empty Tables 207
Empty Tables 478

Although these numbers initially appeared overwhelming, they also suggested an important engineering observation.

The project did not require understanding the entire ERP.

It required understanding only the relatively small subset of entities responsible for employee management.

This realization significantly reduced the scope of the investigation.

Engineering Principle

Reverse engineering should begin by reducing the problem space rather than attempting to understand an entire enterprise system simultaneously.

3.2 When the Database Becomes the Documentation

Commercial ERP systems typically provide implementation documentation describing database relationships, business entities, and application architecture.

No such documentation was available for this project.

Consequently, the database itself became the primary source of information.

Every table, every column, and every record represented evidence from which the application's logical design had to be inferred.

Instead of reading technical documentation, the engineering process relied upon observation, experimentation, and verification.

The database effectively became its own documentation.

3.3 Discovering the Operational Tables

With hundreds of tables available, manually inspecting every object would have been impractical.

A different strategy was therefore adopted.

Rather than beginning with the database, the investigation began with the ERP application's user interface.

Whenever an employee list or operational screen was displayed, the number of records shown by the application was recorded.

These values were then compared against the row counts of every non-empty database table.

Tables containing approximately the same number of records became immediate candidates for further investigation.

Additional heuristics accelerated the process.

Database views were excluded during the initial investigation because they represented derived datasets rather than physical storage.

Fortunately, the ERP followed a relatively consistent naming convention in which database views began with the prefix V, allowing them to be distinguished quickly from operational tables.

Candidate tables were subsequently verified by examining column names, sample records, and their correspondence with information presented through the ERP interface.

Through repeated verification, the operational HR tables gradually emerged from the much larger enterprise schema.

3.4 Reconstructing Relationships

One of the most unexpected discoveries was the apparent absence of database-enforced referential integrity.

Although employee identifiers clearly linked information across multiple tables, the Oracle schema contained virtually no foreign key constraints describing these relationships.

Instead, the ERP appeared to rely entirely upon the application layer to maintain data consistency.

As a result, relationships that would normally be discovered through database metadata instead had to be reconstructed manually by analysing matching identifier values across related tables.

This transformed what initially appeared to be a database exploration exercise into an exercise in reconstructing the underlying data model itself.

Understanding the ERP therefore required reasoning about the stored data rather than relying upon the database engine to describe its own structure.

3.5 Mining Rather Than Exploring

Looking back, the investigation more closely resembled data mining than traditional software development.

The objective was never to understand every table contained within the ERP.

Instead, the objective was to isolate only those entities required to support employee identification, placement, and migration.

Once those entities had been identified, the remaining hundreds of tables became largely irrelevant to the project.

Reducing the problem from an enterprise containing hundreds of database objects to a comparatively small operational subset fundamentally changed the complexity of the engineering effort.

Only after this discovery process was complete could data consolidation begin.

Engineering Insight

Reverse engineering is not the process of understanding everything. It is the disciplined process of discovering only what is necessary to solve the engineering problem at hand.

04. Data Consolidation Architecture

"Finding the data solved one problem. Making it usable solved another."

Identifying the operational tables represented only the first stage of the project.

Employee information still remained distributed across multiple databases developed using different technologies, naming conventions, and application architectures.

Before effective searching could be implemented, these heterogeneous datasets first had to be transformed into a common logical representation.

The objective was not merely to migrate data.

The objective was to create an architecture in which every search algorithm could operate against a consistent information model regardless of the original data source.

4.1 Migration Strategy

The organization maintained employee information within three independent repositories.

  • ERP Database containing official employee and placement information.
  • Legacy HR Database containing historical personnel records.

  • HRDC Database containing staff development and training information.

Because the helper MIS was developed using Laravel and MariaDB, each repository first had to be migrated into a common relational environment.

The migration process consisted of several controlled stages:

  1. Export operational ERP tables from Oracle.
  2. Import them into Microsoft SQL Server.
  3. Transfer the datasets through Microsoft Access using ODBC.
  4. Export each table into MySQL-compatible format.
  5. Import the converted tables into MariaDB.
  6. Import the HR database (originally supplied in Excel format) into MariaDB.

  7. Import the HRDC MySQL database without modification.

Following migration, all three repositories existed within MariaDB while remaining logically independent.

This arrangement simplified development while preserving the original structure of each source system.

4.2 Standardising the Data Model

Although the databases now shared a common database engine, they still differed substantially in schema design.

Field names varied.

Column structures differed.

Employee attributes were distributed across different tables.

Directly querying these heterogeneous structures from the application would have introduced unnecessary complexity into every search operation.

Instead, schema normalization was performed inside the database.

The objective was to ensure that every search algorithm received information presented through a consistent relational interface regardless of the original source.

4.3 Designing Logical Views

Rather than repeatedly constructing complex JOIN operations within application code, two logical database views were created.

Employee View (emp)

The emp view exposed the core employee identity.

It presented employee code, names, father's name, CNIC, contact information, dates of birth, joining dates, and employment status using standardized field names independent of the original ERP schema.

4.4 Unified Search Layer

With each repository transformed into a consistent relational structure, the application no longer needed to distinguish between different databases.

Every search operator returned the same logical column structure regardless of whether the data originated from ERP, HR, or HRDC.

Because the output format remained identical, SQL UNION operations could merge these independent result sets into a single searchable dataset.

From the perspective of the search engine, three heterogeneous databases had effectively become one logical information system.

This separation between data preparation and information retrieval proved fundamental to the architecture.

Future search algorithms could be introduced without redesigning the underlying consolidation layer.

4.5 Architectural Benefits

The resulting architecture provided several practical advantages.

  • Reverse engineering occurred only once.
  • Schema complexity remained isolated inside the database.
  • Application code interacted with a stable relational model.
  • Additional data sources could be incorporated with minimal changes.
  • Search algorithms remained independent of database-specific implementation details.

  • Maintenance effort was significantly reduced because changes to underlying tables rarely affected application logic.

Engineering Insight

Data consolidation is not merely a migration exercise. It is the process of transforming heterogeneous information into a stable representation that allows higher-level algorithms to remain simple, modular, and maintainable.
