Part III — Data Consolidation Architecture

3. Data Consolidation Architecture

Before an effective search system could be developed, the employee information first had to be consolidated into a form that allowed uniform querying. Although the search algorithms received most of the attention, the real engineering challenge was integrating three independent personnel repositories into a single logical information system.

The organization maintained employee information across three different sources:

  • ERP Database (Oracle/SQL Server based), containing official employee, placement, and organizational records.
  • Legacy HR Database, containing historical human resource information maintained before ERP adoption.
  • HRDC Database, containing training and staff development records accumulated over several years.

Together, these repositories contained more than 5,100 employee records distributed across different database engines, schemas, naming conventions, and application architectures.

3.1 Reverse Engineering the ERP

The ERP database presented the greatest challenge.

Rather than providing a concise operational schema, the database contained hundreds of tables, many of which were either empty, automatically generated, or unrelated to the HR module. No foreign key relationships were implemented at the database level, making it impossible to rely on metadata to understand how entities were connected.

Consequently, the database had to be reverse engineered manually.

Instead of studying the application source code—which was unavailable—the investigation began by observing the ERP application's user interface. Information displayed on individual screens was compared with database tables having similar record counts and contents. This iterative process gradually revealed which tables actually stored operational HR data.

Naming conventions also proved useful. Database views followed a consistent prefix, allowing them to be distinguished from physical tables and preventing duplicate investigation of equivalent datasets.

Once the relevant entities had been identified, only the operational tables required for employee search and placement information were extracted.

3.2 Database Migration Strategy

Because the helper MIS was developed using Laravel and MySQL, the ERP data had to be migrated into an open-source environment suitable for rapid development.

The migration process consisted of several stages:

  1. Export the required ERP tables.
  2. Import the tables into Microsoft SQL Server.
  3. Transfer the datasets through Microsoft Access using ODBC.
  4. Export each table into MySQL-compatible format.
  5. Import all converted tables into MariaDB/MySQL.
  6. Repeat the process for the HR database.
  7. Import the HRDC database directly into MySQL.

Although this migration pipeline appears lengthy, it provided complete control over the imported schema while allowing unnecessary enterprise structures to be discarded.

3.3 Creating Logical Views

Even after migration, directly querying dozens of normalized ERP tables would have produced unnecessarily complex application code.

Instead, logical database views were designed.

The first view, emp, exposed the core employee identity by presenting names, CNIC, contact information, dates of birth, and employment status using field names consistent with the other repositories.

The second view, placement, combined placement records with organizational lookup tables including designation, department, employee type, grade, and duty station. By resolving these relationships once inside the database, the application could retrieve complete placement information through a single query rather than repeatedly constructing complex joins.

This approach significantly simplified the application layer while isolating schema complexity inside the database, where it naturally belonged.

3.4 Unified Search Layer

Once every repository had been transformed into a common relational structure, the search engine no longer needed to understand where a record originated.

Instead, each search operator produced results with an identical column structure. SQL UNION operations merged these result sets into a single logical dataset presented to the user.

From the application's perspective, three independent databases had effectively become one searchable information system.

This architectural separation between data preparation and search algorithms proved fundamental. It allowed new search techniques to be introduced later without modifying the underlying data consolidation process, resulting in a system that remained modular, extensible, and considerably easier to maintain.
