07.3 Levenshtein Distance – When Typographical Errors Become the Problem

One of the most powerful techniques available for approximate string matching is the Levenshtein Distance algorithm. Unlike phonetic algorithms such as Soundex, which attempt to match words based on pronunciation, Levenshtein measures the minimum number of character edits required to transform one string into another.

These edit operations typically include:

  • Character insertion
  • Character deletion

  • Character substitution

For example:

Database Value

Ahmad

Ahmed

Muhammad

Instead of asking "Do these two names sound alike?", Levenshtein asks a different question:

"How many typing mistakes separate these two strings?"

This distinction makes it particularly effective when the original data already exists but has been entered with minor spelling variations, accidental omissions, or typographical mistakes.

Why Levenshtein Was Valuable

During the ERP migration, employee information originated from multiple independent systems that had evolved over many years.

Even when referring to the same individual, records frequently differed because of:

  • Manual typing errors
  • Missing characters
  • Additional spaces
  • Different spellings
  • OCR or transcription mistakes

  • Legacy data inconsistencies

Traditional SQL operators cannot recognize these records as similar.

For example,

Muhammad Ali
Mohammad Ali
Muhamad Ali
Muhammed Ali

are clearly recognizable to a human reader, yet an exact SQL comparison treats each value as entirely different.

Levenshtein allows these variations to be compared mathematically.

Engineering Trade-off

Although Levenshtein is an excellent approximate matching algorithm, it comes with a significant computational cost.

Unlike a simple indexed lookup, the algorithm must compare individual characters between two strings while calculating the minimum edit sequence.

As both the number of records and the allowed edit distance increase, the amount of computation rises dramatically.

During development, I performed several practical experiments rather than formal benchmarks. Although the testing environment was not intended for research, one pattern became immediately apparent:

Increasing the permitted edit distance produced a disproportionately large increase in execution time.

A search allowing only one character difference completed relatively quickly.

Allowing two character differences increased execution time substantially.

Beyond that point, search performance deteriorated rapidly and became impractical for interactive use across thousands of employee records.

The exact execution time naturally depended on the dataset and hardware, but the overall trend was unmistakable: greater flexibility demanded exponentially greater computational effort.

Practical Engineering Decision

Rather than maximizing search tolerance, the implementation deliberately limited the allowable edit distance.

In normal operation, the search was restricted to a maximum distance of two.

This provided an effective balance between:

  • Accuracy
  • User responsiveness

  • Computational cost

Whenever larger distances were required, they were executed only as exceptional searches rather than becoming the default behaviour.

This design decision illustrates an important engineering principle:

A theoretically superior algorithm is not necessarily the best engineering solution.

The objective was not to find every mathematically possible match.

The objective was to produce useful results within a reasonable amount of time for operational staff.

Hybrid Optimization

As development progressed, another observation emerged.

Not every search required Levenshtein to examine the entire dataset.

Instead, inexpensive operators such as LIKE could first eliminate the overwhelming majority of unrelated records.

Only the much smaller candidate set would then be evaluated using Levenshtein.

Conceptually, instead of writing separate queries combined with UNION, both conditions could be incorporated into a single SQL statement:

WHERE Name LIKE '%Ali%'
AND LEVENSHTEIN(Name,'Ali') <= 2

This allowed the database optimizer to exploit the inexpensive filter before invoking the computationally expensive comparison.

Although this hybrid approach was introduced later in development, it demonstrated an important optimization strategy:

Use inexpensive algorithms to prune the search space before applying expensive algorithms.

This principle extends far beyond employee search systems and appears throughout computer science, from database optimization to artificial intelligence.

Engineering Principle

Approximate matching is always a balance between flexibility and computational cost.

Allowing greater error tolerance improves the probability of finding the desired record, but every additional degree of flexibility consumes disproportionately more computational resources. Effective engineering lies in identifying the point where additional accuracy no longer justifies its cost.
