Searching Employee Records Across Multiple Databases

Why Exact Matching Is Not Enough

Introduction

Every organization eventually faces a data consistency problem.

Sometimes it begins with a new HR application. Later an ERP is introduced. Older systems continue to exist because they still contain historical information, while newer systems become the official source of truth. Over time, employee information becomes fragmented across multiple databases, each designed independently and optimized for its own purpose.

This was exactly the challenge I encountered while developing an internal Employee Search & Data Consolidation Management Information System (MIS).

The organization maintained employee information in three different systems:

  • ERP Database – The organization's primary Human Resource and Finance system.

  • Legacy HR Database – A standalone HR application used before ERP implementation.

  • HRDC Database – An internal staff database maintained by the Human Resource Development Centre.

Collectively these systems contained more than 5,100 employee records.

Although the ERP became the official HR platform, daily operations revealed a practical problem. Staff members frequently searched for employees whose names were misspelled, entered differently, or existed in multiple systems. The ERP's search mechanism required exact matches. Even a minor spelling mistake, missing space, punctuation mark, or abbreviated name caused the search to fail.

Management needed a practical solution rather than replacing the ERP. My task was to build a helper MIS that could retrieve employee records regardless of which system contained them while tolerating common human errors.

This article describes the engineering decisions behind that solution and explains why combining multiple search techniques produced better results than relying on a single algorithm.

Understanding the Problem

At first glance the problem appeared simple.

"Search an employee."

In reality, searching for an employee required answering several questions.

Which database contains the record?

Was the employee migrated into ERP?

Is the employee only available in the legacy HR system?

Does the spelling exactly match?

Has the employee's CNIC changed?

Was the mobile number updated?

Did HR enter "Muhammad" while another operator entered "Mohammad"?

The search system therefore needed to operate across multiple independent databases while accommodating inconsistencies introduced over many years of manual data entry.

Consolidating Multiple Data Sources

Before any search algorithm could be implemented, the data itself needed to be consolidated.

The ERP database presented the greatest challenge.

Like many enterprise applications, the ERP stored information across a large number of highly normalized tables. Hundreds of tables existed, many of which were either empty, configuration-related, or unrelated to employee information. Without access to the ERP source code, understanding the schema required extensive database analysis.

After identifying the relevant tables, I exported them from SQL Server using ODBC into Microsoft Access before converting them into MySQL-compatible SQL dumps. Once imported into MySQL, I created database views that combined employee, financial, placement, and organizational information into a single logical entity.

This approach significantly simplified the search layer.

Instead of querying dozens of normalized tables every time a user searched for an employee, the application queried a unified database view containing all relevant information.

The same process was repeated for the Legacy HR database and the HRDC database.

Ultimately the search engine operated against three standardized datasets:

  • ERP View

  • HR Database

  • HRDC Database

The application allowed users to search a specific source or query all sources simultaneously.

Why Exact Search Fails

Exact matching is extremely fast.

It is also extremely unforgiving.

Consider the following examples.

Employee record:

Muhammad Abdullah Khan

User searches for:

Mohammad Abdullah Khan

or

Muhammad A. Khan

or

M Abdullah Khan

Although a human immediately recognizes these as the same individual, an exact comparison considers them completely different strings.

This limitation becomes more apparent in multilingual environments where names may be transliterated differently into English.

An exact search should therefore remain available for cases where precise identifiers such as employee IDs or CNIC numbers are known, but it should never be the only search mechanism available.

Expanding Search with SQL LIKE

The next logical improvement was SQL's LIKE operator.

LIKE introduces wildcard matching, allowing partial text searches.

Users can search for fragments of names instead of complete strings.

For example:

Muhammad%

matches:

  • Muhammad Ali

  • Muhammad Khan

  • Muhammad Abdullah

This approach dramatically improves usability while remaining computationally inexpensive.

However, LIKE has important limitations.

Searching for very common prefixes quickly produces hundreds of results.

Searching with extremely short fragments often becomes meaningless.

LIKE is therefore an excellent filtering mechanism but not an intelligent matching algorithm.

Phonetic Matching Using Soundex

Many spelling variations share similar pronunciation.

Soundex converts words into phonetic codes, allowing names with similar pronunciation to produce identical search keys.

For example:

Muhammad

Mohammad

Mohamad

may all produce similar phonetic values.

This significantly improves search quality when users misspell names.

Unfortunately, traditional Soundex works primarily on individual words.

Employee names frequently contain two, three, or even four words.

Applying Soundex independently to each word often failed to produce reliable matches.

Designing a Multi-Word Soundex Function

To overcome this limitation, I implemented a custom database function named soundex_match_all().

Instead of generating a phonetic code for only one word, the function processed each word within a name and compared them collectively.

This produced noticeably better search results for multi-word employee names.

The improvement came at a cost.

The function required nested iterations across both search terms and database values.

As the number of employee records increased, computational complexity also increased.

This reinforced an important engineering lesson:

Accuracy and performance almost always compete with one another.

Measuring Similarity with Levenshtein Distance

Phonetic matching solves pronunciation problems.

It does not solve typographical errors.

Levenshtein Distance measures how many edits are required to transform one string into another.

Examples include:

  • insertion

  • deletion

  • substitution

This allows searches such as:

Abdulah

to correctly match

Abdullah

provided the acceptable distance threshold remains small.

Levenshtein proved particularly useful for correcting accidental typing mistakes.

However, its computational cost grows rapidly when applied across thousands of records.

Choosing an appropriate threshold therefore became critical.

A higher threshold improved flexibility but significantly increased processing time.

Regular Expressions

Regular expressions provided another powerful search mechanism.

Instead of matching exact text, users could search patterns.

Unlike phonetic matching, regular expressions excelled at structured searches where the expected format was known.

They also avoided some of the computational costs associated with recursive similarity calculations.

The challenge shifted from algorithm performance to pattern design.

An overly broad pattern generated excessive results.

An overly restrictive pattern returned nothing.

Carefully designed expressions provided an excellent balance between flexibility and precision.

Combining Multiple Search Strategies

One of the biggest lessons from this project was that no individual algorithm consistently produced the best results.

Each solved a different class of problem.

Exact matching was ideal for identifiers.

LIKE handled partial searches.

Soundex handled pronunciation differences.

Levenshtein corrected typographical errors.

Regular expressions supported structured searches.

Rather than selecting one algorithm, the application allowed users to choose the most appropriate strategy or combine multiple search methods into a unified result set using SQL UNION operations.

This hybrid approach produced substantially better search accuracy while preserving acceptable performance.

Beyond Searching: ERP Data Integration

The project eventually expanded beyond employee retrieval.

Once duplicate records could be identified reliably, another operational challenge emerged.

Creating new employees inside the ERP required navigating multiple screens and manually entering related data.

To streamline onboarding, I developed a companion utility that generated ERP-compatible JSON files.

Users entered employee information once into the helper MIS.

The system then produced structured JSON containing all required relationships and foreign keys expected by the ERP.

Instead of repetitive manual entry, staff could perform bulk imports while maintaining consistent data quality.

Lessons Learned

This project reinforced several principles that continue to influence how I design business systems today.

First, technical problems are often data problems before they become software problems.

Second, consolidating information into a unified logical model simplifies application development far more than writing increasingly complex search queries.

Third, no search algorithm is universally superior. Practical systems benefit from combining multiple techniques rather than searching for a single "perfect" solution.

Finally, successful enterprise software is not measured solely by elegant code. It is measured by how effectively it helps people complete their work with greater accuracy and less effort.

Conclusion

The Employee Search & Data Consolidation MIS transformed fragmented employee information into a unified, searchable platform.

More importantly, it demonstrated that thoughtful data engineering can significantly improve the usability of existing enterprise systems without replacing them.

The project ultimately consolidated more than 5,100 employee records from three independent systems, introduced advanced fuzzy-search capabilities, simplified ERP onboarding through JSON integration, and reduced the operational effort required to locate and manage employee information.

Although developed as an internal tool, the engineering principles behind it—data consolidation, layered search strategies, and practical system integration—are applicable to many organizations facing similar challenges as they modernize legacy information systems.
