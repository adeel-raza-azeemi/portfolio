06. Combining Multiple Search Strategies

While phonetic matching was effective for handling pronunciation differences, it was unable to detect typographical errors where the spelling differed but the pronunciation remained unrelated. Employee names entered manually frequently contained omitted characters, additional characters, transposed letters, or simple typing mistakes. To address this class of errors, the search engine incorporated Levenshtein Distance as an additional matching strategy.

One search algorithm rarely solves the problem of identifying employees across heterogeneous datasets. Each technique performs well under certain conditions and poorly under others. Rather than relying on a single matching strategy, the Employee Search & Data Consolidation MIS applies multiple complementary search methods to the same query, allowing each algorithm to compensate for the limitations of the others.

The objective was not to determine which algorithm was mathematically superior. The objective was to maximize the probability of locating the correct employee record while minimizing the time spent performing repeated searches using different criteria.

For example, a user searching for an employee named Ahmed Ali may encounter several real-world situations:

  • the first name may be misspelled;

  • the surname may be omitted;

  • the employee may have entered only initials;

  • the CNIC may be incomplete;

  • only part of the mobile number may be known;

  • the official record may contain abbreviations or inconsistent spacing.

No single operator performs well across all these situations. LIKE efficiently handles partial text matching but cannot identify spelling mistakes. Soundex tolerates phonetic variations but ignores exact character placement. Levenshtein Distance identifies typographical errors but becomes computationally expensive when applied indiscriminately to large datasets.

Rather than forcing users to understand these differences, the system executes multiple search strategies transparensively and presents a unified result set. From the user's perspective, there is only one search operation. Internally, however, several independent matching techniques work together to increase the likelihood of finding the desired employee.

This design reflects an important engineering principle: users should not need to understand the implementation details of a search engine in order to use it effectively. The complexity belongs inside the software, not in the user's workflow.

Hybrid Filtering for Expensive Algorithms

During practical usage it became evident that computationally intensive algorithms such as Levenshtein Distance and custom multi-word Soundex could become prohibitively expensive when evaluated against an entire employee database.

Instead of executing these algorithms across every record, a hybrid filtering strategy was introduced. Lightweight predicates—typically SQL LIKE expressions—were applied first to eliminate obviously unrelated records. The computationally expensive similarity algorithms were then evaluated only against this significantly smaller candidate set.

Unlike the earlier UNION-based strategy, this optimisation combined multiple predicates within the same SQL statement using logical AND conditions. This allowed the database optimizer to reduce the search space before invoking the more expensive comparison functions.

Although this approach did not fundamentally change the underlying algorithms, it substantially reduced execution time while preserving search quality. It represents a practical example of balancing computational cost against search accuracy, a recurring theme throughout the development of the system.

Engineering Insight

Engineering Principle — Use expensive computation only after inexpensive filters have reduced the search space.

This principle appears in database systems, search engines, compiler optimization, machine learning pipelines, and modern information retrieval systems. Although developed independently for this project, the same philosophy underlies many high-performance search architectures used today.
