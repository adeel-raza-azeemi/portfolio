Part 2 — Reverse Engineering an Undocumented Enterprise Database

4. Understanding the Existing System

Before a search system could be designed, it was first necessary to understand the structure of the Enterprise Resource Planning (ERP) database itself. Although the ERP successfully supported the organization's Human Resources and Finance operations, it offered very little insight into its internal data model. Source code was unavailable, database documentation did not exist, and the vendor treated the underlying schema as proprietary.

Consequently, the first engineering challenge was not software development—it was system discovery.

The objective was straightforward:

Identify where employee information was actually stored and determine how those records could be extracted without modifying the production ERP.

At first glance, this appeared to be a simple database exploration exercise. In reality, it became an exercise in reverse engineering.

4.1 Initial Exploration

Administrative access to the Oracle database server made it possible to inspect the database schema directly.

The first observation immediately revealed the scale of the system.

The ERP database contained:

Object Count
Database Tables 685
Database Views 187
Empty Tables 478
Non-empty Tables 207

From an engineering perspective, these numbers immediately raised an important question.

How many of these tables actually participated in the Human Resource module?

The answer turned out to be: surprisingly few.

Although the ERP exposed hundreds of tables, only a relatively small subset contained employee-related information. The remaining tables represented configuration data, module-specific entities, historical structures, system metadata, or simply remained unused within the organization's deployment.

Rather than attempting to understand every table, the investigation focused only on identifying those that actively supported employee management.

4.2 There Was No Documentation

Many commercial ERP systems provide detailed database documentation for customers or implementation partners.

This system did not.

No entity relationship diagrams were available.

No data dictionary existed.

No documentation described table relationships.

No source code could be inspected to understand how the application interacted with the database.

Every relationship had to be inferred.

This fundamentally changed the engineering approach.

Instead of reading documentation, the database itself became the documentation.

4.3 A Surprising Discovery

One of the most unexpected findings during the investigation was the apparent absence of database-enforced referential integrity.

Despite representing a highly normalized enterprise application, the Oracle schema contained virtually no foreign key constraints linking related tables together.

Primary identifiers were clearly reused across multiple tables, suggesting that logical relationships certainly existed. However, these relationships were enforced entirely by the application rather than by the database management system.

For example, fields representing employee identifiers consistently matched corresponding records in related tables, yet no explicit foreign key definitions were present within the schema.

This observation had two important consequences.

First, understanding relationships required careful examination of the stored data rather than relying on database metadata.

Second, any supporting application developed outside the ERP needed to reconstruct these relationships independently.

In effect, the data model had to be rediscovered.

4.4 Finding the Important Tables

Without documentation or foreign key definitions, a systematic method was required to identify which tables actually supported employee management.

Rather than examining hundreds of tables manually, a data-driven approach was adopted.

The ERP application's user interface became the primary source of clues.

Whenever a list of employees appeared within the application, the corresponding record count was noted.

These counts were then compared against every non-empty database table.

Tables whose row counts closely matched the application's displayed information became immediate candidates for further investigation.

Several additional heuristics significantly accelerated the process.

Database views were intentionally excluded during the initial investigation because they merely represented derived data built upon underlying base tables.

Fortunately, the ERP followed a reasonably consistent naming convention in which view names began with the prefix "V", allowing them to be identified quickly.

Candidate tables were then inspected individually.

Column names, record counts, and data contents were compared against information displayed within the ERP interface.

Through repeated verification, the subset of tables responsible for employee information gradually emerged.

Although this process required patience, it proved significantly more reliable than attempting to understand the entire schema simultaneously.

4.5 Mining Rather Than Exploring

Looking back, the investigation resembled data mining more than traditional software development.

The objective was never to understand every table.

Instead, the objective was to isolate only those entities necessary to support employee search and migration.

Once these tables had been identified, the remaining schema became largely irrelevant to the project.

This principle substantially reduced the complexity of the engineering effort.

Instead of attempting to reverse engineer an entire ERP containing hundreds of tables, the problem was reduced to understanding only the relatively small collection of entities required to reconstruct employee information.

Only after this discovery process was complete could the actual design of the Employee Search MIS begin.
