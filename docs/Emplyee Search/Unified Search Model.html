05. Unified Search Model

"Good search algorithms require good data. Great search systems require good abstractions."

Once employee information had been consolidated into MariaDB and the ERP schema had been simplified through logical database views, a new engineering challenge emerged.

Although the data now resided within a common database engine, the search process itself still remained tightly coupled to the individual structure of each repository.

Each database used different field names.

Some stored employee names as a single field, while others separated first and last names.

Telephone numbers appeared under different column names.

Certain repositories contained information unavailable elsewhere.

If each search algorithm had been written specifically for every database, introducing a new search method would have required implementing and maintaining multiple versions of the same logic.

Such duplication would have significantly increase both software complexity and maintenance effort.

Instead, the project adopted a different approach.

Rather than designing search algorithms around individual databases, the databases were first transformed into a common logical search model.

From that point onward, every search algorithm interacted only with the unified model and remained completely independent of the underlying source systems.

This separation between data representation and search logic became one of the most important architectural decisions of the project.

5.1 Why a Unified Search Model Was Necessary

Searching multiple databases independently presents several practical difficulties.

Each repository may expose different attributes, different naming conventions, and different data completeness.

Consequently, even identical search algorithms often require separate implementations for every data source.

Instead of solving the search problem three times, the project attempted to solve it once.

Every repository was transformed into a consistent logical representation exposing the same searchable attributes, regardless of its original internal structure.

The application therefore interacted with employee information rather than individual databases.

This abstraction significantly simplified subsequent software development.

5.2 Standardising Search Attributes

To support consistent searching, every searchable repository exposed a common set of logical fields.

These included:

  • Employee Code
  • Employee Name
  • Father's Name
  • CNIC
  • Mobile Number
  • Telephone Number
  • Email Address

Although not every repository contained every attribute, each search result followed the same logical structure.

This consistency allowed identical SQL statements to execute against multiple repositories without requiring algorithm-specific modifications.

5.3 Database Independence

A major objective of the architecture was database independence.

Search algorithms should not need to know whether a record originated from the ERP, HR database, or HRDC repository.

Instead, each repository became simply another provider of employee information.

The responsibility for understanding database-specific schemas remained entirely within the database layer through views and field mappings.

Application code therefore became considerably simpler because business logic remained isolated from storage implementation.

5.4 Query Composition

Each search operator generated its own SQL query against the standardized search model.

Rather than selecting a single search strategy, the system executed several complementary strategies independently.

Their result sets were subsequently combined using SQL UNION operations.

Because every query returned identical column structures, SQL UNION could merge all results into a single dataset without additional transformation.

This design also simplified future expansion.

Adding another search algorithm required only generating another compatible query.

No changes were required elsewhere in the application.

5.5 Preparing for Multi-Strategy Retrieval

Separating the search architecture from individual algorithms created an important long-term advantage.

New retrieval strategies could be introduced without redesigning either the database schema or the application interface.

Whether the system employed exact matching, phonetic comparison, regular expressions, edit-distance calculations, or future search techniques, each algorithm operated against the same unified logical representation.

The architecture therefore remained stable while search capabilities continued to evolve.

Looking back, this architectural flexibility proved more valuable than any individual search algorithm implemented during the project.

Engineering Principle

Software architecture should isolate change.
Search algorithms evolve continuously as new techniques emerge. By designing a stable abstraction layer between the databases and the search engine, individual algorithms could be improved, replaced, or extended without affecting the remainder of the system. Good architecture therefore minimizes the cost of future change rather than merely solving today's problem.
