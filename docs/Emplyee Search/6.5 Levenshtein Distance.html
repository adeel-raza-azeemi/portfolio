6.5 Levenshtein Distance

Edit-Distance Based Searching

While previous search techniques focused on exact values, partial matches, phonetic similarity, or structural patterns, Levenshtein Distance approaches the problem from an entirely different perspective. Rather than asking whether two strings match, it measures how many editing operations are required to transform one string into another.

These editing operations typically consist of three fundamental actions:

  • insertion of a character,
  • deletion of a character,

  • substitution of one character for another.

The resulting edit distance provides a numerical measure of similarity. Smaller distances indicate that two strings are more alike, whereas larger distances represent increasingly different values.

For employee records, this proved particularly valuable when data entry mistakes produced names that were neither exact matches nor phonetically equivalent.

Handling Human Typographical Errors

Unlike phonetic algorithms, which assume that different spellings may represent the same pronunciation, Levenshtein Distance addresses a different class of problems: ordinary typing mistakes.

Examples include:

  • omitted characters,
  • duplicated characters,
  • adjacent typing errors,
  • accidental substitutions,

  • minor misspellings introduced during manual data entry.

In operational environments where records have been accumulated over many years by different operators, such inconsistencies become inevitable. Measuring edit distance provides an effective mechanism for recovering these records without requiring perfect input from the user.

Practical Performance Constraints

Although Levenshtein Distance produced highly useful results, it also introduced the greatest computational cost among all search methods implemented within the system.

During development, informal experimentation revealed that increasing the permitted edit distance caused query execution time to grow dramatically. A search allowing one character difference completed relatively quickly, whereas increasing the tolerance to two characters required substantially more processing. Larger distances rapidly became impractical for interactive use.

Rather than performing formal benchmark testing, these observations emerged through repeated operational use while balancing responsiveness against search completeness.

As a result, the implementation deliberately restricted the maximum edit distance to two character modifications during normal searches. This threshold provided an effective compromise between search quality and execution time while maintaining an acceptable user experience.

Hybrid Filtering Strategy

An important optimization emerged during later stages of development.

Instead of executing the computationally expensive Levenshtein comparison across the entire dataset, inexpensive filtering operations were first used to reduce the candidate records.

For example, a broad LIKE condition could first eliminate the majority of obviously unrelated records. Only the remaining subset was then evaluated using Levenshtein Distance.

Unlike the earlier strategy of combining independent searches through UNION, this optimization placed multiple conditions within the same query using logical AND operators. The inexpensive filter naturally reduced the search space before the edit-distance calculation was evaluated.

Conceptually, this mirrors many engineering systems in which coarse filtering precedes more precise analysis. By eliminating unlikely candidates early, computational resources can be concentrated where they provide the greatest benefit.

Engineering Observation

Levenshtein Distance demonstrated that search accuracy cannot be considered independently from computational cost.

Increasing the allowable edit distance undoubtedly discovers more potential matches, but it also expands the search space significantly. Beyond a certain point, the additional computational effort produces diminishing practical benefit.

The implementation therefore favored a conservative threshold that balanced accuracy with responsiveness rather than attempting to recover every theoretically possible match.

Engineering Principle

Similarity-based algorithms should be applied selectively. Restricting expensive comparisons to a carefully filtered subset provides substantially better scalability than applying them indiscriminately across the entire dataset.
